# BUILD QUEUE - AZMARA

Only the AZMARA chat (Claude) writes here, and only after Shakeel says LOCK. Codex builds every WAITING line in order:
at his 01:00 job, or at once when Shakeel types GO in the AZMARA Codex chat. Codex changes only the Status column and
adds the task-note date; he never adds a line. A FAILED line stays until the AZMARA chat decides. Fable checks at 04:15
that every BUILT line has a LOCK record. Newest line at the bottom. A line blocked only by another line not yet BUILT stays WAITING with the note "waits for line N" - never FAILED (Founder, 1 Nov). A line whose Note begins with PRIORITY is built before every other WAITING line in every queue, after the line in progress (Founder, 1 Nov; only Shakeel or Fable quoting him may write it). QUESTION = Codex filed a question in `QUESTIONS.md` beside this file and moved on; the business chat answers and sets the line back to WAITING (rule 10).

**No night approvals, no blanket chains (Founder, 16 Nov 2026; charters rule 15, AD-AIOS-154).** Every new brief states `Needs: none` or `Needs: Founder present - <what>`. Codex never starts a `Founder present` line in the 01:00 run: it stays WAITING with the note "needs daytime GO" and Codex builds the next eligible line; on a daytime GO those lines go first. "Waits for line N" means a real dependency only: a FAILED or QUESTION line holds up only the lines that need its result. Anything stuck more than 24 hours goes to Shakeel in Fable's morning message. **Order is not waiting (Founder, 23 Nov 2026: "when codex is running it doesnt wait for claude while waiting or stuck it moves onto next possible job").** "After N" in a Note or a brief is build order only. If line N is QUESTION, FAILED or needs the Founder, Codex does not wait: it parks N (a held candidate stays in a git-ignored `held/LINE<n>/` folder inside the repo's build folder, never in `~/_to_delete`), builds the next WAITING line, and returns to N when its answer is in - it rechecks QUESTIONS.md after every finished line, applies N on top of the newer code and re-runs N's checks. Only a note that says `NEEDS line N BUILT - <reason>` blocks a line, and the reason must be something the line cannot be built without. A run ends only when no WAITING line can be built. When a line goes to QUESTION, its task note says which line was started next and at what time (or that no other line could be built, and why). **Questions come in one batch (Founder, 23 Nov):** before changing code Codex reads the whole brief, spec and masters and files every question it can see together, not one at a time. **Lessons file (23 Nov 2026):** the short active page is `AGENT_LESSONS_LEARNED_CURRENT_VERSION_V3.md`; an instruction that still names `..._V2.md` means V3 (V2 is archived whole and is not read). **Line budget (Founder, 24 Nov 2026: "check what went wrong and do a deep fix"; ZYRA line 126 held its queue for 37 hours and 11 full test runs).** One line may hold a repo for at most **6 hours or 3 failed full-gate runs**, whichever comes first (the 6 hours count from when the line's owner takes the repo, not from when its chat started; a restart after an answered question starts a new budget - clarified 25 Nov, QUESTIONS 223). Then the owner stops: the candidate goes to `held/LINE<n>/`, one QUESTIONS row marked "For Fable" says what failed and whether the fault is in the app or in the test tool, the line is set to QUESTION and the repo is released so the next WAITING line is built. A full run already in progress when the limit is reached may finish - the stop applies before the next one starts (clarified 24 Nov). A new test that takes more than 10 minutes on this Mac is never part of a line's local gate: it runs on hosted CI or as its own queue line. A run (01:00, 13:00 or GO) that starts no line writes one row per WAITING line in the report saying why it was not started; an owner chat still active when a run starts is named at the top of the report with its age. **One fresh chat per line (Founder, 24 Nov 2026: "do a deep review and try find a fix").** Until 22 Nov every queue line was built in its own new chat: typically 20 to 40 minutes and about 40 million tokens a line (28 ZYRA lines on 12 Nov). On 24 Nov the pinned ZYRA chat, 20 days old and on a legacy model, built every line itself with helpers: 9 lines in about 10.6 hours, about 90 million tokens a line, and it checked on its helpers 1,110 times at about 150,000 tokens a check. From now: (1) **The pinned business chat only coordinates.** It reads the queue, starts **one new chat for each line** (the create-thread tool; the settings-file model at effort **ultra** - Founder 24 Nov, clickable - never a legacy model), gives it the brief path and the line number, and records the result. It does not change code, run tests or start build helpers itself. The line chat may use its own helpers. (2) **Wait cheaply.** While a line chat works, the coordinator uses the longest single wait the tool allows and checks at most once every 10 minutes; it reads the line chat's final report, not its history. (3) Lines in different repos or products may run at the same time (at most 3); lines in the same repo run one after another. (4) A line chat ends when its line is BUILT, QUESTION or FAILED. A line that comes back with its answer gets a new chat that starts from the held candidate. (5) If a new chat cannot be started, the run's task note says so with the exact error - never a silent fall-back to building in the pinned chat. (6) A line already being built when this rule arrives finishes the way it started; the rule applies from the next line. Lessons L50; AD-AIOS-154 addendum 24 Nov.
